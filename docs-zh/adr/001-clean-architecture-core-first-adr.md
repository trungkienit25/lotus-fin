# ADR 001: 整洁架构规范、文件行数 <200 行上限与严禁临时脚本制度

- **状态：** 已通过 (Accepted)
- **适用范围：** Lotus Fin 全量工程代码库与微服务

---

## 1. 决策背景 (Context)
在金融科技与会计核算系统中，野蛮生长的开发模式往往会导致大量临时脚本泛滥（手动热修复补丁脚本、硬编码重算脚本、临时数据提取脚本）。这会导致：
- 核心业务逻辑严重碎片化与失真。
- 缺乏自动化回归测试覆盖，使得账目不一致问题反复重现。
- 代码库体积膨胀，严重挤占人类开发者与 AI 编程智能体的上下文窗口。

---

## 2. 核心架构决策 (Decision)

### 2.1. 核心优先原则（严禁散落临时脚本）
- **严格禁止：** 在既定架构目录边界之外创建散落的临时业务脚本或未经抽象的 utility 工具文件夹。
- **整洁架构分层隔离标准：**
  1. `领域层 (Domain Layer)`：定义纯粹的核心实体、业务校验规则、值对象与财务常量，不依赖任何第三方框架。
  2. `应用/用例层 (Application / UseCase Layer)`：编排业务流转链路、ReAct 智能推理循环、事务提交与并发互斥锁。
  3. `基础设施/交付层 (Infrastructure / Delivery Layer)`：实现具体的数据库网关、多模型 LLM 适配器以及 RESTful 接口控制器。

### 2.2. 强制单文件行数红线：严格限制 < 200 行
- 全量生产环境代码文件必须严格遵守 **单个文件不超过 200 行** 的红线。
- 当文件接近 200 行阈值时，必须进行水平/垂直解耦重构：
  - 用例层拆分为：协调器 (Coordinators) + 规则评估器 (Evaluators) + 查询处理器 (Query Handlers)。
  - 控制器层拆分为：REST 路由端点 + DTO 数据校验器 + 结果序列化适配器。

### 2.3. 必备质量验收标准 (Mandatory Verification)
每一个金融业务用例必须配备双层自动化测试矩阵：
- **单元测试 (Unit Tests)：** 零外部数据库依赖，纯内存秒级验证核心数学公式与边界极限场景。
- **集成测试 (Integration Tests)：** 端到端校验 REST 请求/响应协议封套与数据库账本最终一致性。
