# 🔀 Git 工作流与分支治理规范 — Lotus Fin

本文档规定了 Lotus Fin 代码仓库的分支生命周期管理拓扑结构、保护机制以及约定式提交（Conventional Commits）标准。

---

## 1. 分支拓扑结构

```
  main (生产环境 — 经严格审计验证的稳定发布版)
    │
    ├──────────────────── staging (预发布环境 / 最终用户验收测试 UAT)
    │                       ▲
    │                       │ 测试套件通过后合入
    │                       │
    └──────────────────── develop (持续集成与联调测试分支)
                            ▲
                            │ 模块联调通过后合入
                            │
                    ┌───────┴───────┐
                    │               │
                 feat/            fix/
               cashflow-engine   rate-shock-calc
```

代码合并生命周期遵循严格的单一前向流转链路：
```
feature/fix 功能/缺陷分支 -> develop (集成联调) -> staging (预发布验收) -> main (生产部署)
```

---

## 2. 分支职责划分与保护规则

| 分支名称 | 生命周期与职责 | 检出基础 | 目标合并分支 | 目标发布环境 |
| :--- | :--- | :--- | :--- | :--- |
| **`main`** | 经全面验证的生产级发布版本 | — | 仅允许来自 `staging` | 生产服务器 (80 端口) |
| **`staging`** | 预发布验收与 UAT 全链路验证 | `main` | 经审核的 `feature/*` / `fix/*` | 预发集成集群 |
| **`develop`** | 敏捷集成开发与接口联调 | `main` | 功能开发分支 | 本地 / CI 测试机 |
| **`feat/*`** | 新功能特性开发 | `develop` | `develop` -> `staging` | 本地开发环境 |
| **`fix/*`** | 缺陷与问题修复 | `develop` | `develop` -> `staging` | 本地开发环境 |
| **`hotfix/*`** | 线上突发严重紧急问题修复 | `main` | 同步合并至 `staging` 与 `main` | 紧急补丁发布 |

### 强制保护规范：
1. **严禁直接向 `main`、`staging` 与 `develop` 分支执行强制推送（Direct Push / Force Push）。**
2. 任何代码合入合并请求（PR/MR）之前，必须 100% 通过自动化构建校验（`npm run build`、Python 核心数学测试套件）。

---

## 3. 提交信息规范 (Conventional Commits)

标准格式结构：
```
<type>(<scope>): <简要描述，全小写动宾短语>
```

提交类型枚举（Types）：
- `feat`: 面向用户或业务领域的新增特性功能。
- `fix`: 修复既有模块或逻辑中的缺陷 Bug。
- `docs`: 仅涉及文档、注释的调整与更新。
- `refactor`: 代码重构（既不新增特性，也不修复 Bug 的结构调整）。
- `test`: 补充或修正单元测试、集成测试用例。
- `chore`: 构建流程、依赖版本更新、工程脚手架配置调整。
