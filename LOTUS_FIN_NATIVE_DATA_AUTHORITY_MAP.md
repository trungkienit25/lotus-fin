## Native authority qualification sheet — mandatory before adapter implementation

For each chosen service, record a named Product/Data owner and Security sign-off with:

1. Existing module/service/database and deployment owner; immutable schema/API version and authoritative primary key. If none exists, request approval for a model/migration rather than invent one during integration.
2. Who creates/updates/reverses records; mutation boundary, audit history, tenant membership lifecycle and deletion/retention policy. An importer must identify record ownership after ingestion, synchronization and reconciliation authority; an ERP mirror is not automatically native.
3. Canonical company versus tenant versus site relationship; invoice lifecycle/status mappings, posting/issue/due dates, accounting timezone, currency/rounding, residual versus historical balance, credits/returns/amendments and versioning.
4. Server-side membership, capability, row/document and field policy; query versus exact-document grants; masking, disabled-user/revocation and privileged maintenance separation. No ERP roles or Administrator default in the core path.
5. Observation time, financial cutoff, source revision and freshness SLA; cross-feed consistency/reconciliation rules, cache keys/invalidation and truthful unavailable/partial/empty states. Never infer complete-zero from unavailable data.
6. Product/site/company/source/session/connection version binding, accepted coverage and resource budget; qualified ordinary-user positive/negative gold and source-outage behavior.

Only the first read scope needs the five-field invoice metadata. Amounts, currency, customer, due dates, historical balances and risk must be separately authorized before widening it. Draft/submitted concepts may be mapped only after native lifecycle approval; otherwise version the contract and disclose the difference.

## Excluded false authorities

- `data/external/world_bank_enterprise_surveys/*` and `MANIFEST.md` are external survey context; neither native invoices nor company ledger.
- `docs/features/AI002/fixture_scripts/direct_confirmed_commitments.json` is a test-author declaration; not real settlement authority.
- `setup_data.py`, old ERP gold and browser transport interception produce synthetic or ERP records; do not relabel them as Lotus-owned records.
- Pydantic InvoiceReadDocument, FinancialSnapshot and DTO schemas establish representation/derived output, not a persisted native invoice table or write authority.
- An ERPNext report fetched through a Lotus API still originates in ERPNext. The current namespace does not transfer ownership.

Unresolved assumptions: no external owned data service was supplied, native schema/lifecycle is unspecified, actual data freshness/retention policies and live ordinary-user permissions were not provided. Concurrent frontend changes during final verification do not establish native data ownership or live permission authority; their UI acceptance is unverified. Approval records must close these gaps; this map creates no database, entity implementation or migration.
